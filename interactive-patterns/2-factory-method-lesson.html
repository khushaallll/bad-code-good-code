Factory Method
    Design pattern · Factory Method

    Factory Method

    You already know SOLID and OOP fundamentals, and how Strategy swaps interchangeable behavior. Factory Method is about a different question: not "which behavior do I run", but "which class do I build". Pick a vector store backend below to see the shape before we name it.

    pipeline.py — the code that runs a retrieval query
    factory = ChromaVectorStoreFactory()
    factory.run_query(embedding, top_k=5)
    ChromaVectorStoreFactory builds a ChromaVectorStore, wired to a local host and port.

    Notice what doesn't change when you click a different backend: the second line, run_query. That line has no idea which vector database it's about to talk to. That's Factory Method.

    1 · The problem

    A RAG pipeline that needs to try three vector databases

    You're building the retrieval half of a retrieval-augmented generation pipeline. It embeds a query and looks up the nearest chunks in a vector store. Right now that's ChromaDB, running locally. Your team is about to run a bake-off: the same pipeline needs to run against Qdrant and Pinecone too, so you can compare recall and latency before picking one for production. Each client library wants different constructor arguments and a different method to run a similarity search.

    Coupling — how much one piece of code depends on the specific details of another piece of code. Example: a function that calls chromadb.Client(host, port) directly is tightly coupled to Chroma's constructor — swap the backend, and every call site that constructed a Chroma client has to change too.

    Here's the first version, written back when Chroma was the only option anyone needed.

    2 · The naive version

    Constructors, scattered across the codebase

    Works, until you need a second backend 
    # retrieval.py
import chromadb

def run_query(embedding: list[float], top_k: int) -> list[dict]:
    client = chromadb.Client(host="localhost", port=8000)
    collection = client.get_collection("docs")
    return collection.query(query_embeddings=[embedding], n_results=top_k)

# eval_harness.py — a second, separate call site
def score_pipeline(queries: list[dict]) -> float:
    client = chromadb.Client(host="localhost", port=8000)  # duplicated
    collection = client.get_collection("docs")
    # ... run each query, compare against a labeled set ...

    When the Qdrant bake-off ticket lands, here's what it actually costs:

    • Both run_query and score_pipeline call chromadb.Client(...) directly. Adding Qdrant means finding every one of these call sites and rewriting each one — and any you miss keeps quietly running against Chroma.
    • There's no single place that owns "how do we build a vector store client." That knowledge is duplicated wherever a client gets constructed, so a change to connection settings (a new auth token, a new port) means another find-and-replace across the codebase.
    • You can't parametrize the backend at runtime — say, from a config file or an environment variable — without threading an if/elif into every function that currently calls chromadb.Client(...) directly.
    • Testing run_query in isolation means either standing up a real Chroma instance or patching the exact line chromadb.Client(...) inside the function — there's no seam to inject a fake client through.

    3 · Building the fix, one step at a time

    From scattered constructors to one designated builder

    Step 1 — pull construction into one function

    The smallest useful move: stop calling chromadb.Client(...) everywhere, and call one function instead.

    def build_chroma_collection():
    client = chromadb.Client(host="localhost", port=8000)
    return client.get_collection("docs")

# both call sites now call this instead of constructing a client themselves

    This is a simple factory — one function that owns construction. It already fixes the duplication problem. But if you add a backend parameter and an if/elif inside build_chroma_collection to also handle Qdrant and Pinecone, you're back to editing one growing function every time a backend is added — the same shape of problem as Section 2, just moved to a single location instead of scattered across several. Factory Method fixes the deeper issue: it makes adding a backend mean writing new code, not editing a shared function.

    Step 2 — separate "what a vector store can do" from "which one you have"

    Interface — a contract that says which methods a class must provide, without saying how they work. Example: "anything that claims to be a vector store must have a query(embedding, top_k) method that returns matches" — that's the whole contract.

    In Python, you write an interface with abc.ABC (Abstract Base Class) and @abstractmethod. A class that inherits from it without implementing every abstract method can't be instantiated.

    from abc import ABC, abstractmethod

### Product — what every backend must be able to do
class VectorStore(ABC):
    """The contract every vector store backend must satisfy."""

    @abstractmethod
    def query(self, embedding: list[float], top_k: int) -> list[dict]:
        """Return the top_k nearest matches to embedding."""
        ...

    In Factory Method's own vocabulary, VectorStore is called the Product — the thing being built.

    Step 3 — one class per backend, implementing that contract

    Concrete product — a class that implements the product interface with one specific backend's behavior. Example: ChromaVectorStore is a concrete product — it's one specific way of satisfying VectorStore's contract. 
    class ChromaVectorStore(VectorStore):
    def __init__(self, host: str, port: int) -> None:
        import chromadb
        self._collection = chromadb.Client(host=host, port=port).get_collection("docs")

    def query(self, embedding: list[float], top_k: int) -> list[dict]:
        return self._collection.query(query_embeddings=[embedding], n_results=top_k)


class QdrantVectorStore(VectorStore):
    def __init__(self, url: str, collection_name: str) -> None:
        import qdrant_client
        self._client = qdrant_client.QdrantClient(url=url)
        self._collection_name = collection_name

    def query(self, embedding: list[float], top_k: int) -> list[dict]:
        return self._client.search(self._collection_name, query_vector=embedding, limit=top_k)

    Step 4 — a designated builder for each product, sharing one orchestration method

    Factory method — a method whose only job is to construct and return an object, so the calling code never has to call a constructor directly. Example: create_store() below is a factory method — it's the one place responsible for deciding which VectorStore subclass to build and how to configure it.
    Creator — a class that contains a factory method, plus whatever surrounding logic needs the object that factory method produces. Example: VectorStoreFactory below is the Creator — it owns create_store() and run_query(), but never mentions ChromaVectorStore or QdrantVectorStore by name.
    Polymorphism — calling the same method name on different objects and getting each object's own behavior, without checking which type you're holding. Example: self.create_store() below returns a ChromaVectorStore when called on ChromaVectorStoreFactory, or a QdrantVectorStore when called on QdrantVectorStoreFactory — run_query never checks which one it got. 
    ### Creator — owns the factory method, plus logic that uses its result
class VectorStoreFactory(ABC):
    """Builds a VectorStore and runs queries against it, without knowing which backend it is."""

    @abstractmethod
    def create_store(self) -> VectorStore:
        """The factory method — subclasses override this and nothing else."""
        ...

    def run_query(self, embedding: list[float], top_k: int) -> list[dict]:
        """Same for every backend — construction is the only part that varies."""
        store = self.create_store()
        return store.query(embedding, top_k)


### Concrete creators — each overrides create_store, and nothing else
class ChromaVectorStoreFactory(VectorStoreFactory):
    def create_store(self) -> VectorStore:
        return ChromaVectorStore(host="localhost", port=8000)


class QdrantVectorStoreFactory(VectorStoreFactory):
    def create_store(self) -> VectorStore:
        return QdrantVectorStore(url="http://localhost:6333", collection_name="docs")


# usage — pipeline.py and eval_harness.py both call this, never a constructor
factory = ChromaVectorStoreFactory()
results = factory.run_query(embedding, top_k=5)

# bake-off: swap the backend by swapping which factory you build
factory = QdrantVectorStoreFactory()
results = factory.run_query(embedding, top_k=5)

    run_query is written exactly once, on VectorStoreFactory. Adding Pinecone means writing PineconeVectorStore and PineconeVectorStoreFactory — two new classes — and touching nothing that already exists.

    4 · The shape of it

    Two hierarchies, joined by one "creates" relationship

    Dashed line + arrow = inherits / implements. Dotted gold line + arrow = creates — the one thing the Creator's factory method is responsible for.

    Two independent hierarchies, not one. ChromaVectorStoreFactory knows about ChromaVectorStore — that pairing is the whole point of overriding create_store(). But VectorStoreFactory itself, and its shared run_query method, only ever touch the VectorStore product interface at the top of the lower tree.

    Checkpoint

    Correct. run_query lives on VectorStoreFactory, and every concrete creator inherits it unchanged. The only way that one method body can work for Chroma, Qdrant, and Pinecone alike is by asking self for the product through the overridden factory method, rather than naming a specific class.
    Not quite — that's not a language rule. Python doesn't require calling abstract methods anywhere in particular; this is a design choice, made so the shared method stays backend-agnostic.
    Not quite — Python allows direct construction anywhere. The problem isn't legality, it's that direct construction inside the shared run_query would pin it to one backend, defeating the point of having subclasses at all.
    Not quite. If run_query constructed ChromaVectorStore(...) directly, every concrete creator's inherited run_query would always return Chroma results, regardless of which subclass you called it on — QdrantVectorStoreFactory().run_query(...) would silently query Chroma.

    5 · Predict the output

    What does this print?

    Assume each product's query is mocked to just tag its backend, so you can trace the call without a real database:

    class QdrantVectorStore(VectorStore):
    def query(self, embedding, top_k):
        return f"[qdrant] top {top_k} matches"

class PineconeVectorStore(VectorStore):
    def query(self, embedding, top_k):
        return f"[pinecone] top {top_k} matches"

class QdrantVectorStoreFactory(VectorStoreFactory):
    def create_store(self):
        return QdrantVectorStore()

    def create_store(self):
        return PineconeVectorStore()

factory = QdrantVectorStoreFactory()
print(factory.run_query(embedding=[0.1, 0.2], top_k=3))

factory = PineconeVectorStoreFactory()
print(factory.run_query(embedding=[0.1, 0.2], top_k=3))

    Write down what the two print calls output before opening the answer. Remember: run_query itself is only defined once, on VectorStoreFactory.

    Reveal answer 
    [qdrant] top 3 matches
[pinecone] top 3 matches

    Each factory is a different concrete creator, so self.create_store() resolves polymorphically to that creator's own override — QdrantVectorStore() the first time, PineconeVectorStore() the second. run_query's own code never changed between the two calls; only which object create_store() handed back changed.

    6 · Same shape, different domain

    This isn't a vector-database-specific trick

    Factory Method shows up anywhere a class needs an object built for it, and the exact class to build should stay swappable. Two more, from unrelated domains:

    Payments — checkout gateways

    A checkout flow needs to charge through Stripe today and Adyen for European customers next quarter, with the actual charging logic staying identical either way.

    class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amount_cents: int) -> str: ...

class StripeGateway(PaymentGateway):
    def charge(self, amount_cents: int) -> str:
        ...  # call Stripe's API

class PaymentGatewayFactory(ABC):
    @abstractmethod
    def create_gateway(self) -> PaymentGateway: ...

    def checkout(self, amount_cents: int) -> str:
        gateway = self.create_gateway()
        return gateway.charge(amount_cents)

class StripeGatewayFactory(PaymentGatewayFactory):
    def create_gateway(self) -> PaymentGateway:
        return StripeGateway()

    checkout plays the same role run_query did — written once, works for every gateway.

    Data ingestion — document parsers

    An ingestion pipeline needs to extract text from PDFs today, with Markdown and HTML sources coming as the pipeline grows.

    class DocumentParser(ABC):
    @abstractmethod
    def parse(self, raw_bytes: bytes) -> str: ...

class PdfParser(DocumentParser):
    def parse(self, raw_bytes: bytes) -> str:
        ...  # extract text from PDF bytes

class DocumentParserFactory(ABC):
    @abstractmethod
    def create_parser(self) -> DocumentParser: ...

    def extract_text(self, raw_bytes: bytes) -> str:
        parser = self.create_parser()
        return parser.parse(raw_bytes)

class PdfParserFactory(DocumentParserFactory):
    def create_parser(self) -> DocumentParser:
        return PdfParser()

    Same shape again: DocumentParserFactory never names PdfParser — only PdfParserFactory does.

    Three domains, one shape: a Creator (VectorStoreFactory, PaymentGatewayFactory, DocumentParserFactory) has one shared method that needs a Product, gets it from an overridable factory method, and never names a concrete Product class itself.

    You've probably already used this without naming it

    Python's standard library is full of classmethods — methods called on the class itself, not an instance — whose entire job is to build and return an object, as an alternative to calling __init__ directly:

    Path.home()
datetime.fromtimestamp(0)
dict.fromkeys(["a", "b"], 0)

    Each of these is a factory method: a designated method whose whole purpose is constructing an instance in one particular way, chosen instead of calling Path(...) or datetime(...) with the right arguments yourself. You don't get an abstract Creator/Product hierarchy for free this way — but the core idea, a method whose job is "build me one of these", is exactly what create_store() was doing above.

    Checkpoint
    Is Path.home() an example of the Factory Method idea?
    Correct. What makes something a factory method is its job — a dedicated method that builds and returns an object instead of calling the constructor at the call site — not whether it sits inside a full abstract Creator/Product hierarchy. Path.home() plays exactly that role.
    Not quite. The abstract Creator/Product hierarchy from this lesson is the classic GoF shape, useful when you need several interchangeable creators. The core idea — a method dedicated to building an object — doesn't require that whole structure to still count.
    Not quite. A classmethod takes cls instead of self, but it's still a method whose job is producing an instance — that's the relevant similarity, not the exact parameter name.
    Not quite — no wrapper is needed. Path.home() already plays the factory-method role on its own; adding a class around it wouldn't change what it does, just add ceremony.

    7 · Spot the smell

    This code has Creator and Product classes — but something's wrong

    class ChromaVectorStoreFactory(VectorStoreFactory):
    def create_store(self) -> VectorStore:
        return ChromaVectorStore(host="localhost", port=8000)

    def run_query(self, embedding: list[float], top_k: int) -> list[dict]:
        store = ChromaVectorStore(host="localhost", port=8000)
        return store.query(embedding, top_k)

    ChromaVectorStoreFactory correctly overrides create_store. Something's still wrong here. What is it, and what happens the day someone changes how VectorStoreFactory.run_query works for everyone else?

    Reveal explanation

    The bug: ChromaVectorStoreFactory overrides run_query too, and inside it, constructs ChromaVectorStore(...) directly instead of calling self.create_store() — duplicating the exact object-building code that create_store already contains, right next to it.

    The day someone changes the shared VectorStoreFactory.run_query — say, to add retry logic or logging around every query, for every backend — ChromaVectorStoreFactory won't get that change. Its own copy of run_query shadows the base class's version and has to be updated by hand, separately, or it quietly falls out of sync with every other backend. The fix is to delete this override entirely and let ChromaVectorStoreFactory inherit run_query from VectorStoreFactory unchanged — the whole reason create_store exists is so subclasses never need to touch run_query at all.

    8 · Trade-offs

    When not to reach for Factory Method

    Factory Method costs you a Product interface, a Creator base class, and at least one concrete pair — more files and more indirection than a single constructor call. That's worth it once you have, or clearly expect, more than one thing to build. It's not worth it when you don't.

    Over-engineered 
    class VectorStore(ABC):
    @abstractmethod
    def query(self, embedding, top_k): ...

class ChromaVectorStore(VectorStore):
    ...

class VectorStoreFactory(ABC):
    @abstractmethod
    def create_store(self) -> VectorStore: ...

class ChromaVectorStoreFactory(VectorStoreFactory):
    def create_store(self) -> VectorStore:
        return ChromaVectorStore(host="localhost", port=8000)

    If this is a personal project or a prototype with a hard commitment to ChromaDB and no bake-off on the roadmap, this is four classes for something a single function already says: def build_store(): return ChromaVectorStore(host="localhost", port=8000). Reach for Factory Method when a second concrete product is real or clearly coming — not "vector databases might theoretically change one day."

    Factory Method vs. Abstract Factory — easy to mix up

    Both hide constructor calls behind a method. The difference is how many related objects get built, and whether they're built together.

    Factory MethodAbstract Factory
    What it buildsOne product, via one overridden method (create_store() → a VectorStore)A family of related products, via several methods on one factory object
    ExampleChromaVectorStoreFactory builds a ChromaVectorStore, nothing elseA ChromaBackendFactory might expose get_store(), get_embedder(), get_reranker() — all guaranteed to be Chroma-compatible with each other
    How variation happensSubclassing the CreatorComposing several factory methods behind one object, often without subclassing at all
    One-line rule: building one kind of object, varied by subclass, is Factory Method. Building several related objects together, so they're guaranteed to match each other, is Abstract Factory.

    9 · Cheat sheet & practice

    Cheat sheet

    Problem it solves
    Object construction scattered across the codebase, so adding a new type means hunting down every call site — or one growing if/elif inside a single constructor function.
    Core idea, in one sentence
    Give the class that needs an object a dedicated method for building it, let subclasses override just that method, and write the surrounding logic once against the product interface.
    Trade-off
    A Product interface, a Creator base class, and at least one concrete pair — real structure for a problem that might only ever need one concrete type.
    The smell that tells you to reach for it
    The same constructor call, or an if/elif choosing which class to instantiate, repeated across multiple functions or files — and a new type means editing all of them.
