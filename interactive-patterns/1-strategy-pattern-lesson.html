Strategy pattern
    Design pattern · Strategy

    Strategy

    You already know SOLID and OOP fundamentals. This lesson builds one pattern from a real production problem, in Python, with checkpoints along the way. Pick a provider below to see the shape of the problem before we name it.

    client.py — the code that sends the request
    strategy = OpenAIStrategy()
    client = LLMClient(strategy)
    client.ask("Summarize this outage.")
    OpenAI's API expects a messages list and returns a choices array.

    Notice what doesn't change when you click a different provider: the last two lines. That's the whole point of this lesson.

    1 · The problem

    An LLM gateway that talks to three different APIs

    You're building an internal service, llm-gateway, that other teams inside your company call when they need a text completion. Today it only calls OpenAI. Product wants two more things this quarter: fail over to Anthropic's API when OpenAI is down, and run some traffic through a self-hosted vLLM model to cut cost. Each of these three APIs wants a different request shape, a different way of reading the auth key, and a different response format to parse.

    Coupling — how much one piece of code depends on the specific details of another piece of code. Example: a function that knows OpenAI's exact JSON field names is tightly coupled to OpenAI's API — change that API's shape, and the function breaks.

    Here's the first version your team shipped, back when there was only one provider to worry about.

    2 · The naive version

    One function, one growing if/elif chain

    Gets the job done, badly 
    import requests

def generate_completion(provider: str, prompt: str, api_key: str) -> str:
    if provider == "openai":
        resp = requests.post(
            "https://api.openai.com/v1/chat/completions",
            headers={"Authorization": f"Bearer {api_key}"},
            json={"model": "gpt-4o", "messages": [{"role": "user", "content": prompt}]},
        )
        return resp.json()["choices"][0]["message"]["content"]

    elif provider == "anthropic":
        resp = requests.post(
            "https://api.anthropic.com/v1/messages",
            headers={"x-api-key": api_key, "anthropic-version": "2023-06-01"},
            json={"model": "claude-sonnet", "max_tokens": 1024,
                  "messages": [{"role": "user", "content": prompt}]},
        )
        return resp.json()["content"][0]["text"]

    elif provider == "local_vllm":
        resp = requests.post(
            "http://gpu-box:8000/generate",
            json={"prompt": prompt, "max_tokens": 1024},
        )
        return resp.json()["text"][0]

    else:
        raise ValueError(f"Unknown provider: {provider}")

    This is a God object in function form — a single unit that has taken on responsibility for everything, instead of one clear job. Here's exactly what that costs you:

    • Add a fourth provider (say, Mistral's API) and you must open generate_completion and edit a function that's already shipped and already tested. Every new provider is a change to old, working code.
    • This one function now has three separate reasons to change: OpenAI changes their JSON shape, Anthropic changes theirs, or vLLM's server changes its route. A change to any provider's API risks breaking the other two branches by accident.
    • You cannot unit-test the Anthropic branch in isolation. Testing it means calling into a 40-line function and hoping your mocks patch the right requests.post call among three.
    • You cannot swap providers per-request without threading a raw string like "openai" through your whole codebase, with no compiler or type checker to catch a typo like "opneai".

    3 · Building the fix, one step at a time

    From if/elif to something you can extend without editing

    Step 1 — pull each branch into its own function

    Before introducing any new vocabulary, do the smallest useful thing: split the if/elif branches apart. This alone doesn't fix the design, but it makes what's wrong easier to see.

    def _call_openai(prompt: str, api_key: str) -> str:
    # ... same body as the openai branch above
    ...

def _call_anthropic(prompt: str, api_key: str) -> str:
    # ... same body as the anthropic branch above
    ...

def generate_completion(provider: str, prompt: str, api_key: str) -> str:
    if provider == "openai":
        return _call_openai(prompt, api_key)
    elif provider == "anthropic":
        return _call_anthropic(prompt, api_key)
    # ...

    generate_completion is still coupled to every provider — it still has to know all three names and dispatch to them by hand. Splitting the functions apart didn't remove that dispatcher; it just tidied it. The real fix is to stop dispatching by string at all.

    Step 2 — define what every provider must be able to do

    Interface — a contract that says which methods a class must provide, without saying how they work. Example: "anything that claims to be a provider must have a generate(prompt) method that returns a string" — that's the whole contract.

    In Python, you write an interface with abc.ABC (Abstract Base Class) and @abstractmethod. A class that inherits from it and doesn't implement the abstract method can't be instantiated — Python enforces the contract for you.

    from abc import ABC, abstractmethod

class LLMProviderStrategy(ABC):
    """The contract every LLM provider must satisfy."""

    @abstractmethod
    def generate(self, prompt: str) -> str:
        """Send `prompt` to this provider and return the completion text."""
        ...

    Step 3 — one class per provider, each implementing that contract

    Concrete strategy — a class that implements an interface with one specific algorithm or behavior. Example: OpenAIStrategy is a concrete strategy — it's one specific way of satisfying LLMProviderStrategy's contract.
    Polymorphism — calling the same method name on different objects and getting each object's own behavior, without checking which type you're holding. Example: strategy.generate(prompt) runs OpenAI's HTTP call if strategy is an OpenAIStrategy, or vLLM's call if it's a LocalVLLMStrategy — same line of calling code either way. 
    class OpenAIStrategy(LLMProviderStrategy):
    def __init__(self, api_key: str) -> None:
        self.api_key = api_key

    def generate(self, prompt: str) -> str:
        resp = requests.post(
            "https://api.openai.com/v1/chat/completions",
            headers={"Authorization": f"Bearer {self.api_key}"},
            json={"model": "gpt-4o", "messages": [{"role": "user", "content": prompt}]},
        )
        return resp.json()["choices"][0]["message"]["content"]


class AnthropicStrategy(LLMProviderStrategy):
    def __init__(self, api_key: str) -> None:
        self.api_key = api_key

    def generate(self, prompt: str) -> str:
        resp = requests.post(
            "https://api.anthropic.com/v1/messages",
            headers={"x-api-key": self.api_key, "anthropic-version": "2023-06-01"},
            json={"model": "claude-sonnet", "max_tokens": 1024,
                  "messages": [{"role": "user", "content": prompt}]},
        )
        return resp.json()["content"][0]["text"]


class LocalVLLMStrategy(LLMProviderStrategy):
    def __init__(self, host: str = "http://gpu-box:8000") -> None:
        self.host = host

    def generate(self, prompt: str) -> str:
        resp = requests.post(f"{self.host}/generate", json={"prompt": prompt, "max_tokens": 1024})
        return resp.json()["text"][0]

    Each class hides its own request shape, its own auth header, its own response parsing. None of them know the other two exist.

    Step 4 — one class that holds a strategy and delegates to it

    Context object — the class that holds a reference to a strategy and calls it, instead of implementing the behavior itself. Example: LLMClient below is the context — it never contains any provider's HTTP details.
    Composition over inheritance — building behavior by holding a reference to another object (composition), rather than inheriting from a base class that hard-codes the behavior. Example: LLMClient doesn't inherit from OpenAIStrategy — it holds one as self._strategy and can swap it for a different object at runtime. 
    class LLMClient:
    """Context: sends prompts through whichever provider strategy it's given."""

    def __init__(self, strategy: LLMProviderStrategy) -> None:
        self._strategy = strategy

    def set_strategy(self, strategy: LLMProviderStrategy) -> None:
        """Swap providers at runtime — e.g. failing over from OpenAI to Anthropic."""
        self._strategy = strategy

    def ask(self, prompt: str) -> str:
        return self._strategy.generate(prompt)


# usage
client = LLMClient(OpenAIStrategy(api_key="sk-..."))
client.ask("Summarize this outage.")

# fail over — LLMClient's code above never changes
client.set_strategy(AnthropicStrategy(api_key="sk-ant-..."))
client.ask("Summarize this outage.")

    Adding a fourth provider now means writing one new class that implements generate. You never touch LLMClient, and you never touch the other providers' classes. That's the whole trade you just made: a longer if/elif chain became a fixed context class plus one small, independent class per provider.

    Checkpoint

    Not quite. The interface defines one shared method, generate, that every strategy implements in its own way. Adding a provider-specific method name to the interface would force every existing strategy (OpenAI, Anthropic, vLLM) to also implement a method they don't need.
    Correct. That's the entire point of the interface: any class that implements generate(prompt) -> str can be handed to LLMClient unchanged.     4 · The shape of it

    Class relationships for this example

    Solid line + diamond = composition ("has a"). Dashed line + arrow = realizes the interface ("implements").

    LLMClient holds one LLMProviderStrategy at a time. It never points at OpenAIStrategy directly — that would put it back in the coupled world from Section 2.

    The first ask call runs through whatever self._strategy is at that moment — an AnthropicStrategy instance, set in the constructor. set_strategy then replaces self._strategy with a new OpenAIStrategy instance, so the second ask call runs polymorphically through that one instead.     6 · Same shape, different domain

    This isn't an LLM-specific trick

    Strategy shows up anywhere you have one job with several interchangeable ways of doing it. Two more, from unrelated domains:

    Payments — checkout

    A checkout flow needs to charge a customer by credit card, PayPal, or a stored wallet balance — and the set of payment methods will keep growing.

    class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount_cents: int) -> bool: ...

class CreditCardStrategy(PaymentStrategy):
    def pay(self, amount_cents: int) -> bool:
        # charge via card network
        ...

class Checkout:
    def __init__(self, method: PaymentStrategy) -> None:
        self.method = method

    def complete(self, amount_cents: int) -> bool:
        return self.method.pay(amount_cents)

    Checkout is the context, exactly like LLMClient was. It never checks isinstance(method, CreditCardStrategy).

    Data pipelines — compression

    A data pipeline writes large batch files to storage, and needs to pick a compression algorithm per job: fast-but-larger for hot data, slow-but-smaller for cold archives.

    class CompressionStrategy(ABC):
    @abstractmethod
    def compress(self, data: bytes) -> bytes: ...

class GzipStrategy(CompressionStrategy):
    def compress(self, data: bytes) -> bytes:
        import gzip
        return gzip.compress(data)

class BatchWriter:
    def __init__(self, compressor: CompressionStrategy) -> None:
        self.compressor = compressor

    def write(self, data: bytes, path: str) -> None:
        compressed = self.compressor.compress(data)
        # ... write `compressed` to `path`

    BatchWriter doesn't know or care whether it's holding gzip, zstd, or a not-yet-written Lz4Strategy.

    Three domains, one shape: a context (LLMClient, Checkout, BatchWriter) holds an interchangeable object behind a shared interface, and delegates the actual work to it.

    You've probably already used this without naming it

    Python's built-in sorted() takes a key argument — a function that decides how to compare elements:

    sorted(users, key=lambda u: u.signup_date)
sorted(users, key=lambda u: u.last_name)

    The function you pass as key is a strategy — it's the interchangeable "how do we compare two things" behavior, and sorted() is the context that calls it without caring which comparison function it was handed. Python just lets you pass a bare function instead of writing a whole class, because functions are objects too — but the shape underneath is the same pattern.

    Checkpoint

Python lets that behavior be a plain function instead of a class instance; the pattern doesn't require any particular syntax, just that shape.
    Not quite. abc.ABC is one way to write an interface in Python, useful when you want the language to enforce the contract. It's not a requirement of the pattern itself — plenty of languages, and plenty of idiomatic Python, express Strategy with plain callables instead.
    Not quite. The pattern is about the relationship between a context and interchangeable behavior, not about whether the context was written by you or by the standard library. sorted() plays the context role here regardless of who wrote it.
    Not quite — no rewrite is needed. Wrapping the lambda in a class would just be a more verbose way of expressing the exact same relationship that already exists.

    7 · Spot the smell

    This code uses Strategy-shaped classes — but something's wrong

    class LLMClient:
    def __init__(self, strategy: LLMProviderStrategy) -> None:
        self._strategy = strategy

    def ask(self, prompt: str) -> str:
        if isinstance(self._strategy, OpenAIStrategy):
            return self._strategy.generate(prompt, model="gpt-4o-mini")
        elif isinstance(self._strategy, AnthropicStrategy):
            return self._strategy.generate(prompt, thinking=False)
        return self._strategy.generate(prompt)

    Every class involved still exists — LLMProviderStrategy, OpenAIStrategy, AnthropicStrategy. Something has still gone wrong. What is it, and what would you have to do to add a fourth provider here?

    Reveal explanation

    The bug: LLMClient.ask branches on isinstance() to decide how to call generate. That's the if/elif chain from Section 2, just moved one level down and disguised behind interface-shaped classes. LLMClient now knows about OpenAIStrategy and AnthropicStrategy by name again — the exact coupling the pattern exists to remove.

    Adding a fourth provider still means editing LLMClient.ask to add another elif. Nothing was actually gained over the original bad version; the classes are decoration on top of the same problem. The fix is to give every strategy's generate the exact same signature, and let each class swallow its own provider-specific options internally (for example, in __init__) instead of leaking them into the context's call site.

    8 · Trade-offs

    When not to reach for Strategy

    Strategy costs you something: an interface, at least one concrete class, and a context that delegates instead of doing the work directly — more files and more indirection than a single function. That cost is worth it when you have, or clearly expect, more than one interchangeable behavior. It's not worth it when you don't.

    Over-engineered 
    class TaxStrategy(ABC):
    @abstractmethod
    def calculate(self, subtotal: float) -> float: ...

class IrishVatStrategy(TaxStrategy):
    def calculate(self, subtotal: float) -> float:
        return subtotal * 0.23

class Invoice:
    def __init__(self, tax_strategy: TaxStrategy = IrishVatStrategy()) -> None:
        self.tax_strategy = tax_strategy

    If this business only ever operates under one fixed VAT rate, with no product plan to support other tax rules, this is three extra moving parts for a calculation that will only ever be called one way. A plain method, def calculate_tax(subtotal): return subtotal * 0.23, says the same thing with nothing to navigate through. Reach for Strategy when a second implementation is real or clearly coming — not "might theoretically happen someday."

    Strategy vs. State — easy to mix up

    Both patterns hold a swappable object behind a shared interface. The difference is who decides when the object changes, and whether the swappable objects know about each other.

    StrategyState
    Who picks the objectThe client, from outside (LLMClient(OpenAIStrategy()))The object itself, from inside, in reaction to what happened
    Do the objects know each otherNo — OpenAIStrategy has no idea AnthropicStrategy existsOften yes — a PendingState may explicitly transition itself to ShippedState
    What it modelsInterchangeable ways to do the same jobAn object's behavior changing as it moves through a lifecycle
    One-line rule: if you choose the variant when you construct or configure the object, it's Strategy. If the object changes its own behavior over time as it transitions between states, it's State.

    9 · Cheat sheet & practice

    Cheat sheet

    Problem it solves
    Swapping between interchangeable algorithms or behaviors, without touching the code that uses them.
    Core idea, in one sentence
    Put each variant behind its own class implementing a shared interface, and hand the context object whichever one it should use.
    Trade-off
    More classes and one extra layer of indirection, for a problem that might only ever have one real implementation.
    The smell that tells you to reach for it
    A function with an if/elif or switch statement selecting between algorithm variants, that gets a new branch every time a variant is added.
