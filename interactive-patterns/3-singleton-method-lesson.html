Singleton

Make sure a class can only ever have one object in memory, and give every part of your program the same way to reach that one object.

01The problem

One config, read from three places

You are building the backend for a checkout service. It has three modules: payment_service.py, checkout_service.py, and shipping_service.py.

All three need the same settings: the payment provider's API key, a feature flag called new_tax_engine, and the current environment name ("staging" or "production"). These settings live in environment variables, read once at startup.

A class is a blueprint for creating objects. It defines what data an object holds and what it can do. An instance is one actual object built from that blueprint — if Config is the blueprint, then Config() called once produces one instance, sitting at one address in memory.

The obvious first design: a Config class. Each module imports it and creates its own instance. That is the version you will look at next, and the version that breaks.

02The bad code

Three modules, three separate configs

Here is the first version. Config reads the environment when it is built. Each module that needs settings just builds its own copy.

config.py — version 1
# config.py
import os

class Config:
    def __init__(self):
        self.api_key = os.environ.get("PAYMENT_API_KEY")
        self.environment = os.environ.get("APP_ENV", "production")
        self.new_tax_engine = os.environ.get("NEW_TAX_ENGINE") == "true"
three call sites
# payment_service.py
from config import Config
config = Config()  # reads env vars, builds object #1

# checkout_service.py
from config import Config
config = Config()  # reads env vars again, builds object #2

# shipping_service.py
from config import Config
config = Config()  # reads env vars again, builds object #3
Why this breaks in production

Each Config() call builds a brand new object. The three objects are not linked in any way. Nothing stops them from disagreeing.

Say an operator flips NEW_TAX_ENGINE to "true" mid-deploy, while old and new pods are both running. payment_service.py might read the flag as off. checkout_service.py, started a second later, might read it as on. One checkout flow now computes tax two different ways in the same request.

Nothing in the code says these three objects are supposed to be the same thing. The class allows unlimited instances, so the bug is invisible until it fires.

Checkpoint

Three files each run config = Config(). What is the real production risk?

03Building the fix

Let the class control its own creation

The fix is to stop letting the caller decide how many Config objects exist. Instead, the class decides. Every call to Config(), from anywhere in the program, should hand back the same object. This is the Singleton pattern: a class that guarantees only one instance of itself ever exists, and gives a single, predictable way to reach it.

Step 1 — override __new__

In Python, calling Config() actually runs two methods in order: __new__, which builds the raw object, and then __init__, which sets it up. Most classes never touch __new__ — Python's default version just allocates a fresh object every time. Singleton works by overriding that default, so object creation is no longer automatic.

config.py — step 1, not yet thread-safe
class Config:
    _instance = None  # class attribute: shared by the class, not per-object

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

A class attribute belongs to the class itself, not to any one object. Config._instance is one shared slot, visible to every call to Config(). The first call finds it empty (None), builds the real object, and stores it there. Every later call finds it already filled, and just returns what is already there.

Checkpoint

Why does __new__ check if cls._instance is None before building?

Step 2 — make it safe under concurrent requests

A checkout service usually runs many requests at once, often on multiple threads — separate paths of execution running inside the same process, able to run at almost the same moment. Two threads can both call Config() for the first time at nearly the same instant, before either one has finished setting _instance.

This creates a race condition: a bug that only happens because of the exact timing of two things happening at once. Thread A checks _instance is None and gets True. Before A finishes building the object, thread B also checks and also gets True. Now both threads build their own object, and the whole guarantee is broken.

The fix is a lock: an object that only one thread can hold at a time. Any other thread that tries to acquire a held lock simply waits until it is released. Wrapping the check-and-build step in a lock makes it atomic — meaning no other thread can step in partway through.

config.py — final, thread-safe version
# config.py
"""Application-wide configuration, loaded once from the environment."""

import os
import threading
from typing import Optional


class Config:
    """Holds settings read from environment variables.

    Config() always returns the same object. The first call reads
    the environment and builds it; every later call, from any module,
    receives that same object back.
    """

    _instance: Optional["Config"] = None
    _lock: threading.Lock = threading.Lock()

    def __new__(cls) -> "Config":
        if cls._instance is None:
            with cls._lock:
                # Second check: another thread may have built it
                # while this thread was waiting for the lock.
                if cls._instance is None:
                    cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self) -> None:
        # __init__ runs on every Config() call, even for the
        # existing instance — so only set up state once.
        if getattr(self, "_initialized", False):
            return
        self.api_key: Optional[str] = os.environ.get("PAYMENT_API_KEY")
        self.environment: str = os.environ.get("APP_ENV", "production")
        self.new_tax_engine: bool = os.environ.get("NEW_TAX_ENGINE") == "true"
        self._initialized = True

Notice the check appears twice: once before the lock, once inside it. The outer check is a fast path — once _instance exists, every later call skips the lock entirely, which matters because acquiring a lock has a small cost every time. The inner check, taken while holding the lock, is what actually closes the race: it catches the case where another thread finished building the object while this thread was waiting to get in.

This two-check shape has a name: double-checked locking. It is worth recognizing by name, because it is a very common thing to be asked to explain or write in an interview.

Checkpoint

Two threads call Config() at the same moment, while _instance is still None. Without the lock, what goes wrong?

Predict the output

Given the final Config class above, what does this print?

predict_output.py
c1 = Config()
c1.new_tax_engine = True

c2 = Config()
print(c2.new_tax_engine)
print(c1 is c2)
Reveal the answer

True, then True.

c1 and c2 are two variable names pointing at the exact same object. Setting c1.new_tax_engine = True changes that one object. When c2 is built, __new__ hands back that same object rather than building a new one, so c2.new_tax_engine already reads True. The is operator checks whether two names point at the same object in memory — here, they do.

04Real world

You have already used this pattern

Singleton shows up constantly in real systems, usually for the same reason as the config example: something needs to be read the same way, and stay in sync, everywhere it is used.

Logging pipeline

logging.getLogger

Python's built-in logging module keeps an internal registry of loggers by name. Calling logging.getLogger("checkout") from ten different files all returns the exact same Logger object.

That is what lets you set the log level once, from anywhere, and have every module's log calls respect it — because they are all writing through the same object.

log = logging.getLogger("checkout")
Persistence layer

One shared connection pool

A database connection is expensive to open. Real services create one connection pool — for example a SQLAlchemy Engine — at startup, and every request borrows a connection from that same pool.

If each request built its own pool instead, the database would quickly run out of connections under load. One shared instance is not an optimization here — it is a requirement.

engine = get_engine()
You already used this, without naming it

Every Python module is already a Singleton. The first time anything does import config, Python runs the file top to bottom and caches the resulting module object in sys.modules. Every later import config, anywhere in the program, returns that exact same cached object instead of re-running the file. That is the same one-object guarantee Singleton gives a class — built into the language itself.

A more Pythonic way to write it

The __new__ override above is the classic version, and it is worth knowing because it is the version most often asked for in interviews. In real Python codebases, the same guarantee is often written more simply, using a decorator — a function that wraps another function to add behavior to it without changing its code.

config.py — functools.lru_cache version
from functools import lru_cache

class Config:
    def __init__(self) -> None:
        self.api_key = os.environ.get("PAYMENT_API_KEY")
        self.environment = os.environ.get("APP_ENV", "production")

@lru_cache(maxsize=1)
def get_config() -> Config:
    """Return the one shared Config, building it on first call."""
    return Config()

lru_cache(maxsize=1) remembers the return value of the first call to get_config() and hands back that same cached value on every later call, instead of running the function body again. The class itself stays ordinary. Calling code writes get_config() instead of Config(), which also makes it visually obvious that something shared is being fetched, rather than a fresh object being built.

05Trade-offs

When Singleton is the wrong call

Singleton creates global state: data that any part of the program can reach and change, from anywhere, without it showing up as a parameter. That is exactly what makes it useful for something like config. It is also exactly what makes it dangerous for the wrong kind of data.

Overuse example

Imagine making ShoppingCart a Singleton, the same way as Config. There should be one cart per user, not one for the entire running application. Built as a Singleton, every user's add_item() call would land in the exact same cart object — one customer would see another customer's items. The pattern is only correct when "exactly one, for the whole program" is actually true of the thing being modeled. A cart fails that test; config passes it.

Two more costs are worth naming directly:

  • Hidden dependencies. A function that calls get_config() internally does not show that dependency in its signature. Reading def calculate_tax(order): does not tell you it secretly also depends on Config.
  • Harder testing. To test calculate_tax with the tax engine flag both on and off, you now have to reach in and mutate the shared Config object between tests, and reset it afterward — instead of just passing a different value in.

The usual fix, when this pain shows up, is dependency injection: instead of a function reaching for the shared instance itself, the caller passes it in explicitly — calculate_tax(order, config) rather than calculate_tax(order). You still build Config as a Singleton once, at startup, and hand that same object to whatever needs it. You just stop letting code fetch it invisibly from the inside.

Singleton vs. a plain global variable

These are often confused, especially in Python, where a module is already a Singleton by construction.

Plain global variableSingleton class
A module-level name like config = Config(), built once, at import time. A class that actively refuses to build a second instance, no matter how many times it is called.
Nothing stops another file from writing config = Config() again, creating a second object under the same name in a different module. Every Config() call, anywhere, is guaranteed to return the same object — the uniqueness is enforced by the class itself, not by convention.
Simple, and often enough — many real Python codebases use exactly this. Worth the extra code only when several different files might construct the object, and the single-instance rule must hold no matter who writes it.

One-line rule: reach for a plain module-level global first; reach for the full Singleton class only when you cannot trust every call site to just reuse the existing object on its own.

06Practice

Spot the bug

This version compiles and runs. It has a real bug, and it is a famous one for this pattern. Find it before revealing the answer.

config.py — broken
class Config:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self):
        self.api_key = os.environ.get("PAYMENT_API_KEY")
        self.new_tax_engine = os.environ.get("NEW_TAX_ENGINE") == "true"
        self.request_count = 0

# elsewhere in the program:
c1 = Config()
c1.request_count += 1
c1.request_count += 1
# ... later, in a completely different module:
c2 = Config()
print(c2.request_count)
Reveal the bug

This prints 0, not 2, even though c1 and c2 are the same object.

__new__ only controls whether a new object gets built. It says nothing about __init__. Python calls __init__ on every Config() call, including calls that receive the existing, already-built object. So building c2 runs __init__ again on the same object, and self.request_count = 0 silently resets the counter c1 had already incremented to 2.

The fix is the guard used in the working version earlier in this lesson: check a flag like self._initialized at the top of __init__, and return immediately if it is already set, so setup logic only ever runs once, no matter how many times Config() is called.

Your turn — MetricsCollector

A data pipeline has several stages: extract.py, transform.py, and load.py. Each stage needs to report timing and row-count metrics as it runs — for example, "extract took 4.2s and produced 10,000 rows."

Build a MetricsCollector class as a Singleton, so that all three stages report into the same in-memory list of events, and a single flush() call at the end of the pipeline can send everything collected, from every stage, in one batch.

  • Use the __new__ override, with the double-checked lock, exactly as shown earlier in this lesson.
  • Give it a record(stage: str, seconds: float, rows: int) -> None method that appends an event.
  • Give it a flush() -> list method that returns all collected events and clears the internal list.
  • Remember the bug from the exercise above: make sure the internal event list is only created once, not reset on every MetricsCollector() call.
07Summary

Cheat sheet

Problem it solves
Guarantees a class has exactly one instance, reachable the same way from anywhere in the program.
Core idea
The class controls its own creation, through __new__, and hands back the same stored object on every call instead of building a new one.
Trade-off
Introduces global, mutable state — which hides dependencies between modules and makes tests harder to isolate.
Smell that tells you to reach for it
Several unrelated files would each independently build "the config" / "the connection pool" / "the logger" — and they must, without question, all share the exact same state.
