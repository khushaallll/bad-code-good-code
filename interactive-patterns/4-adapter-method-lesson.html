Adapter
    Design pattern · Adapter

    Adapter

    You already know Strategy (swap interchangeable behavior) and Factory Method (swap which class gets built). Adapter answers a different question: what do you do when the class you need to plug in already exists — written by someone else, with a shape you can't change? Pick a logging backend below to see it before we name it.

    orders_service.py — the code that logs an event
    sink = ConsoleLogSink()
    OrderService(sink).place_order("A-1001")
    ConsoleLogSink already speaks our LogSink interface directly — no adapting needed.

    Notice what doesn't change: OrderService never mentions Datadog or syslog by name. It only ever calls sink.write(...). That's Adapter.

    1 · The problem

    Your services need to log events. Every logging backend speaks a different language.

    You're building OrderService for an e-commerce backend. Every time an order is placed, it needs to log that event. Your company already runs two logging systems: Datadog, a commercial monitoring SaaS reached through their Python SDK, and an old internal syslog library that predates the team. Datadog's client wants a send_event(title, text, tags, alert_type) call. The legacy syslog library wants emit(priority, line) — a numeric severity and one preformatted string. You don't own either of these libraries' code, and you can't change their method signatures.

    Coupling — how much one piece of code depends on the specific details of another piece of code. Example: a function that calls datadog_client.send_event(title=..., text=..., tags=..., alert_type=...) directly is tightly coupled to Datadog's exact method name and argument shape — swap the backend, and every call site built around that shape breaks.

    Here's the first version, written when Datadog and syslog both had to be supported from day one.

    2 · The naive version

    One class, wired directly to two incompatible vendor APIs

    Works, until a third backend or a second call site shows up 
    # vendor SDKs — code you don't own, can't change
class DatadogClient:
    def send_event(self, title, text, tags, alert_type):
        ...  # calls Datadog's real API

class LegacySyslog:
    def emit(self, priority, line):
        ...  # writes to the syslog daemon


# our code
class BadOrderService:
    def __init__(self, datadog: DatadogClient, syslog: LegacySyslog) -> None:
        self._datadog = datadog
        self._syslog = syslog

    def place_order(self, order_id: str) -> None:
        self._datadog.send_event(
            title="orders: INFO",
            text=f"order {order_id} placed",
            tags=["service:orders", "level:info"],
            alert_type="info",
        )
        self._syslog.emit(6, f"orders order {order_id} placed")

    Ran once, it prints correctly:

    [datadog] INFO | orders: INFO | order A-1001 placed | tags=['service:orders', 'level:info']
[syslog] <6> orders order A-1001 placed

    But here's exactly what this costs you:

    • BadOrderService has to know both send_event's keyword arguments and emit's numeric priority scheme. That's two vendor-specific formats memorized inside one class that's supposed to be about placing orders.
    • A third service — say, BillingService — needs the exact same two log calls. Copy this logic in, and now the Datadog argument order and the syslog priority-6-means-info mapping are duplicated in two places. Datadog changes alert_type's allowed values, and you have to find and fix every call site.
    • Add a third backend, like shipping logs to Kafka, and every class that logs — OrderService, BillingService, and whatever comes next — needs a third block of vendor-specific code added by hand.
    • You can't unit-test place_order's logging behavior without either running a real Datadog client or writing a mock that knows Datadog's exact keyword arguments — there's no shared, simple interface to fake.

    3 · Building the fix, one step at a time

    From vendor calls inline to one shared logging interface

    Step 1 — pull each vendor call into its own function

    The smallest useful move: stop calling datadog.send_event(...) and syslog.emit(...) inline, and call a function instead.

    def send_to_datadog(client: DatadogClient, level: str, message: str, service: str) -> None:
    client.send_event(
        title=f"{service}: {level}",
        text=message,
        tags=[f"service:{service}", f"level:{level.lower()}"],
        alert_type=level.lower(),
    )

def send_to_syslog(syslog: LegacySyslog, level: str, message: str, service: str) -> None:
    priority = 3 if level == "ERROR" else 6
    syslog.emit(priority, f"{service} {message}")

    Both functions now take the same three logical arguments — level, message, service — and translate them into whatever DatadogClient or LegacySyslog actually needs. This already removes the duplication problem. But OrderService would still have to import both functions and call whichever one matches the backend it was given — the caller still has to know which function goes with which vendor object. Adapter finishes the job: it makes every backend look like the exact same type from the caller's point of view.

    Step 2 — name the shape our code actually wants to call

    Interface — a contract that says which methods a class must provide, without saying how they work. Example: "anything that claims to be a log sink must have a write(record) method" — that's the whole contract.
    Target interface — in Adapter specifically, the interface that the calling code already expects and was written against. Example: LogSink below is the target interface — it's the only logging shape OrderService will ever be written to call.

    In Python, you write an interface with abc.ABC (Abstract Base Class) and @abstractmethod. A class that inherits from it without implementing every abstract method can't be instantiated.

    from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass(frozen=True)
class LogRecord:
    """One log event, in our application's own vocabulary."""
    level: str
    message: str
    service: str

class LogSink(ABC):
    """Target interface: the only logging API our services know."""

    @abstractmethod
    def write(self, record: LogRecord) -> None:
        """Deliver record to some destination."""
        ...

    Any backend that already speaks this shape natively needs nothing else:

    class ConsoleLogSink(LogSink):
    def write(self, record: LogRecord) -> None:
        print(f"[console] {record.level} {record.service}: {record.message}")

    Step 3 — wrap each vendor class so it also speaks LogSink

    Adaptee — the existing class with the incompatible interface that you can't or don't want to change. Example: DatadogClient and LegacySyslog are adaptees — they already work, they're just shaped wrong for our code to call directly.
    Adapter — a class that implements the target interface by holding an adaptee and translating each call into the adaptee's own method calls. Example: DatadogSinkAdapter below implements LogSink.write by translating a LogRecord into the exact keyword arguments DatadogClient.send_event expects.
    Composition over inheritance — building behavior by holding a reference to another object (composition), rather than inheriting from it. Example: DatadogSinkAdapter doesn't inherit from DatadogClient — it holds one as self._client and calls methods on it. 
    class DatadogSinkAdapter(LogSink):
    """Adapts DatadogClient to the LogSink interface."""

    _ALERT_TYPES = {"INFO": "info", "ERROR": "error"}

    def __init__(self, client: DatadogClient) -> None:
        self._client = client

    def write(self, record: LogRecord) -> None:
        self._client.send_event(
            title=f"{record.service}: {record.level}",
            text=record.message,
            tags=[f"service:{record.service}", f"level:{record.level.lower()}"],
            alert_type=self._ALERT_TYPES.get(record.level, "info"),
        )


class SyslogSinkAdapter(LogSink):
    """Adapts LegacySyslog to the LogSink interface."""

    _PRIORITIES = {"INFO": 6, "ERROR": 3}

    def __init__(self, syslog: LegacySyslog) -> None:
        self._syslog = syslog

    def write(self, record: LogRecord) -> None:
        priority = self._PRIORITIES.get(record.level, 6)
        self._syslog.emit(priority, f"{record.service} {record.message}")

    DatadogSinkAdapter and SyslogSinkAdapter each hold one adaptee and do one job: turn a LogRecord into whatever call that adaptee actually needs.

    Step 4 — the calling code only ever sees LogSink

    class OrderService:
    def __init__(self, sink: LogSink) -> None:
        self._sink = sink

    def place_order(self, order_id: str) -> None:
        self._sink.write(LogRecord("INFO", f"order {order_id} placed", "orders"))


# usage — same call, three different sinks
for sink in (ConsoleLogSink(), DatadogSinkAdapter(DatadogClient()), SyslogSinkAdapter(LegacySyslog())):
    OrderService(sink).place_order("A-1001")
    [console] INFO orders: order A-1001 placed
[datadog] INFO | orders: INFO | order A-1001 placed | tags=['service:orders', 'level:info']
[syslog] <6> orders order A-1001 placed

    OrderService.place_order never mentions DatadogClient, send_event, LegacySyslog, or emit. It calls self._sink.write(...) exactly once, and each adapter handles its own vendor's translation. Add Kafka next quarter, and it's one new adapter class — OrderService stays untouched.

    Checkpoint
    Your team adds Kafka as a third logging backend. With the design above, what has to change?
    Not quite. place_order only calls self._sink.write(...) — it has no backend branches to add. If you find yourself editing it for a new backend, the design has slid back toward BadOrderService.
    Not quite. LogSink defines one shared method, write, that every adapter implements in its own way. A backend-specific method name on the interface would force ConsoleLogSink, DatadogSinkAdapter, and SyslogSinkAdapter to all implement a method they don't need.
    Correct. That's the entire point of the target interface: any class that implements write(record) -> None can be handed to OrderService unchanged. KafkaSinkAdapter holds a Kafka producer as its adaptee and does the translation, same as DatadogSinkAdapter does for DatadogClient.
    Not quite. DatadogSinkAdapter's whole job is adapting DatadogClient to LogSink — stuffing Kafka logic into it would make one adapter respons­ible for two unrelated vendors. A new adaptee always gets its own adapter class.

    4 · The shape of it

    One interface, two adapters, two vendor classes underneath

    Dashed line + arrow = implements the interface. Solid gold line = holds a reference to (composition). The dashed-border boxes are vendor code we don't own — only the adapters ever touch them.

    OrderService only ever points at LogSink. DatadogSinkAdapter is the one place in the codebase that knows DatadogClient.send_event exists — that knowledge never leaks any further than the adapter that holds it.

    Checkpoint
    Why does DatadogSinkAdapter hold a DatadogClient as a field, instead of inheriting from it?
    Not quite — that's not a Python restriction. You can inherit from most third-party classes. The reason to avoid it here is about what inheriting would actually give you, not a language limitation.
    Correct. DatadogSinkAdapter needs to be a LogSink — that's what lets OrderService accept it — while still being able to call DatadogClient's methods internally. Composition gives you both: inherit from LogSink for the interface, hold a DatadogClient instance for the delegation.
    Not quite — there's no meaningful performance difference between the two here. The reason is about which interface the object ends up satisfying, not speed.
    Not quite. If DatadogSinkAdapter inherited from DatadogClient instead of LogSink, it would have send_event, not write — OrderService couldn't call it as a LogSink at all.

    5 · Predict the output

    What does this print?

    Recall DatadogSinkAdapter._ALERT_TYPES and SyslogSinkAdapter._PRIORITIES only have entries for "INFO" and "ERROR", and both use .get(record.level, default) to fall back when a level isn't in the map:

    records = [
    LogRecord("ERROR", "payment declined", "billing"),
    LogRecord("DEBUG", "cache warmed", "billing"),
]

for sink in (DatadogSinkAdapter(DatadogClient()), SyslogSinkAdapter(LegacySyslog())):
    for record in records:
        sink.write(record)

    Write down what this prints before opening the answer. Pay attention to what happens for the "DEBUG" record specifically — it's not in either adapter's map.

    Reveal answer 
    [datadog] ERROR | billing: ERROR | payment declined | tags=['service:billing', 'level:error']
[datadog] INFO | billing: DEBUG | cache warmed | tags=['service:billing', 'level:debug']
[syslog] <3> billing payment declined
[syslog] <6> billing cache warmed

    For "ERROR", both adapters find a match in their map: Datadog sends alert_type="error", syslog sends priority 3. For "DEBUG", neither map has an entry, so .get(record.level, default) falls back — Datadog's default is "info", syslog's is 6. Notice the record's own level field still says "DEBUG" in the Datadog title (f"{record.service}: {record.level}") even though the alert_type sent to Datadog's API silently became "info" — the adapter's fallback affects the vendor call, not the original data.

    6 · Same shape, different domain

    This isn't a logging-specific trick

    Adapter shows up anywhere your code has a shape it wants to call, and the class you actually need to use wasn't written for that shape. Two more, from unrelated domains:

    Payments — a legacy bank gateway

    A checkout flow wants a clean charge(amount_cents, currency) call. The only integration available for one regional bank is an old gateway library that takes a decimal-string amount and an uppercase currency code, and returns a status dictionary instead of a boolean.

    class PaymentProcessor(ABC):
    @abstractmethod
    def charge(self, amount_cents: int, currency: str) -> bool: ...

# adaptee — a library we don't control
class LegacyBankGateway:
    def make_payment(self, amount: str, currency_code: str) -> dict[str, str]:
        ...  # returns {"status": "OK", "amount": amount}

class LegacyBankGatewayAdapter(PaymentProcessor):
    def __init__(self, gateway: LegacyBankGateway) -> None:
        self._gateway = gateway

    def charge(self, amount_cents: int, currency: str) -> bool:
        amount = f"{amount_cents / 100:.2f}"
        response = self._gateway.make_payment(amount, currency.upper())
        return response["status"] == "OK"
    print(LegacyBankGatewayAdapter(LegacyBankGateway()).charge(1250, "eur"))
# [bank] make_payment('12.50', 'EUR')
# True

    The checkout code calls charge(1250, "eur") — cents, lowercase currency, expects a bool — and never learns that LegacyBankGateway wants a decimal string, an uppercase code, and hands back a dict.

    RAG pipelines — a one-text-at-a-time encoder

    A retrieval pipeline's Embedder interface expects embed(texts) -> list of vectors, batched. A locally-hosted model's client only exposes encode_one(text) -> vector, one text at a time.

    class Embedder(ABC):
    @abstractmethod
    def embed(self, texts: list[str]) -> list[list[float]]: ...

# adaptee
class LocalEncoder:
    def encode_one(self, text: str) -> list[float]:
        ...  # one vector per call

class LocalEncoderAdapter(Embedder):
    def __init__(self, encoder: LocalEncoder) -> None:
        self._encoder = encoder

    def embed(self, texts: list[str]) -> list[list[float]]:
        return [self._encoder.encode_one(t) for t in texts]

    LocalEncoderAdapter.embed absorbs the batch-vs-single-text mismatch by looping — the rest of the pipeline never has to know LocalEncoder can only handle one text at a time.

    Three domains, one shape: our code was written against a target interface (LogSink, PaymentProcessor, Embedder), and an adapter (DatadogSinkAdapter, LegacyBankGatewayAdapter, LocalEncoderAdapter) sits between that interface and an adaptee we can't rewrite.

    You've probably already used this without naming it

    Python's io.TextIOWrapper is a built-in adapter. A raw BytesIO stream only gives you bytes:

    raw = io.BytesIO(b"order A-1001 placed\n")
print(type(raw.read()))
# <class 'bytes'>

raw.seek(0)
text = io.TextIOWrapper(raw, encoding="utf-8")
first = text.read()
print(type(first), repr(first))
# <class 'str'> 'order A-1001 placed\n'

    TextIOWrapper is exactly a LogSink-style adapter: it holds the raw byte stream as its adaptee, and exposes a text-based read/write interface — the shape most of Python's text-handling code actually expects — by decoding bytes to str on the way through. Code that reads text never touches bytes directly.

    Checkpoint
    Is io.TextIOWrapper playing the role of Adapter, Target interface, or Adaptee in the example above?
    Not quite — that's BytesIO's role, not TextIOWrapper's. BytesIO is the adaptee: the thing with bytes-only behavior that needs wrapping.
    Correct. TextIOWrapper(raw, ...) takes a raw byte stream in its constructor — exactly like DatadogSinkAdapter(DatadogClient()) takes a DatadogClient — and its own read/write methods translate to and from the adaptee's bytes-only methods.
    Not quite. There's no single abstract class here playing that role explicitly — but conceptually, "something with text-based read/write" is the shape being targeted, and TextIOWrapper is what supplies it.
    Not quite. A pattern doesn't need to reference the Gang of Four to count — what matters is the shape: does something hold an incompatible object and translate calls into the shape you actually wanted? That's what's happening here, regardless of when the classes were written.

    7 · Spot the smell

    This is called an adapter — but something's wrong

    class LeakyDatadogSinkAdapter(LogSink):
    def __init__(self, client: DatadogClient) -> None:
        self._client = client

    def write(self, title: str, text: str, tags: list[str], alert_type: str) -> None:
        self._client.send_event(title, text, tags, alert_type)

    LeakyDatadogSinkAdapter inherits from LogSink and holds a DatadogClient, exactly like DatadogSinkAdapter did. Something's still wrong. What happens when OrderService tries to use it?

    Reveal explanation 
    OrderService(LeakyDatadogSinkAdapter(DatadogClient())).place_order("A-1001")
# TypeError: LeakyDatadogSinkAdapter.write() missing 3 required positional
# arguments: 'text', 'tags', and 'alert_type'

    The bug: write's signature here is write(self, title, text, tags, alert_type) — Datadog's own parameter shape — instead of write(self, record: LogRecord), the shape LogSink actually declares. OrderService.place_order calls self._sink.write(LogRecord(...)) — one positional argument — so this "adapter" crashes with a TypeError the moment it's actually used.

    This isn't a small typo — it's the adapter failing at its one job. An adapter's whole purpose is to absorb the adaptee's shape internally and expose the target's shape externally. Here, the adaptee's shape leaked straight through the method signature instead of being translated inside the method body. The fix is DatadogSinkAdapter's original signature: accept one LogRecord, and do the unpacking into title/text/tags/alert_type inside write, not in its parameter list.

    8 · Trade-offs

    When not to reach for Adapter

    Adapter costs you an extra class and an extra layer of indirection between your code and the thing it's actually calling. That's worth it when the adaptee's shape is genuinely wrong for your code and you can't or shouldn't change it. It's not worth it when you could just change the mismatched code directly.

    Over-engineered 
    # a class you wrote yourself, in this same codebase
class ReportBuilder:
    def build_rpt(self, data: dict) -> str:
        ...

class Builder(ABC):
    @abstractmethod
    def build(self, data: dict) -> str: ...

class ReportBuilderAdapter(Builder):
    def __init__(self, inner: ReportBuilder) -> None:
        self._inner = inner

    def build(self, data: dict) -> str:
        return self._inner.build_rpt(data)

    ReportBuilder isn't a vendor SDK or a legacy library outside your control — it's a class in the same codebase, written by your own team. If its method is just misnamed (build_rpt instead of build), the fix is to rename the method, not to wrap it in a permanent adapter. Reach for Adapter when you genuinely can't change the adaptee — it's third-party, generated, or shared with other consumers you'd break — not when a rename would do.

    Adapter vs. Decorator — easy to mix up

    Both wrap an object and hold a reference to it. The difference is why you're wrapping it.

    AdapterDecorator
    Interface of the wrapped objectDifferent from what the wrapper exposes — that's the whole reason it existsSame as what the wrapper exposes — a LogSink wrapping a LogSink
    GoalMake an incompatible class usable at allAdd behavior (retry, caching, logging) around a class that already fits
    ExampleDatadogSinkAdapter makes DatadogClient usable as a LogSinkA RetryingLogSink(LogSink) that wraps any other LogSink and retries on failure
    One-line rule: if the wrapped object's interface doesn't match what you need, it's Adapter. If it already matches and you're wrapping it to add behavior around the same interface, it's Decorator.

    9 · Cheat sheet & practice

    Cheat sheet

    Problem it solves
    A class you need to use has an interface that doesn't match what your code expects to call, and you can't or shouldn't change that class.
    Core idea, in one sentence
    Write a class that implements the interface your code expects, holds the incompatible class internally, and translates each call into that class's own method calls.
    Trade-off
    One more class and one more layer of indirection, for a mismatch you could sometimes fix more directly by editing the mismatched code yourself.
    The smell that tells you to reach for it
    Your code needs to call a class whose method names, argument shapes, or return types don't match what the rest of your codebase expects — and that class is third-party, generated, or otherwise off-limits to edit.

    Your turn

    Scenario: you're building a WeatherService for an app that shows current conditions. Your code was written against a clean internal shape: get_current(lat, lon) -> WeatherReading, where WeatherReading has temperature_celsius, humidity_percent, and description fields. The only weather data source available is a third-party SDK, LegacyMetClient, whose one method is fetch(latitude: float, longitude: float) -> dict, returning a dictionary shaped like {"temp_f": 71.6, "rh": 0.42, "summary": "clear"} — Fahrenheit, humidity as a 0–1 fraction, and a different key name for the description.

    Task: apply Adapter to this. Name the target interface and the method it requires. Name the adaptee. Name the adapter class, and describe exactly what conversions it has to perform inside its one method — the temperature scale, the humidity representation, and the field renaming — so that the rest of WeatherService never has to know LegacyMetClient exists. You don't need to write the implementation — just describe it clearly enough that you could code it from your own description.
