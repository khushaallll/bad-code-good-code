Observer
    Design pattern · Observer

    Observer

    You already know Strategy, Factory Method, Adapter, and Decorator — patterns about one object's behavior or shape. Observer is about something else: how does one object announce "something changed" to a group of other objects, without knowing in advance how many there are or what they do? Pick a subscriber list below to see it before we name it.

    order_service.py — the code that changes an order's status
    tracker.attach(EmailNotifier("a@b.com"))
    tracker.set_status("shipped")
    Only EmailNotifier is subscribed. set_status only ever reaches one place.

    Notice what doesn't change: tracker.set_status("shipped"). Whoever is subscribed at that moment gets told — one observer, three observers, it's the same call either way. That's Observer.

    1 · The problem

    An order tracker that several unrelated systems need to react to

    You're building the part of an e-commerce backend that tracks an order's status — placed, shipped, delivered, cancelled. The moment that status changes, several completely separate systems need to react: email the customer, text the customer, and tell the warehouse to update its shelves. More consumers are already planned — an analytics system that logs every status change for reporting.

    Coupling — how much one piece of code depends on the specific details of another piece of code. Example: code that constructs and calls EmailService, SMSService, and WarehouseService by name is tightly coupled to all three — add a fourth system, and that code has to change again.

    Here's the first version, written when only email, SMS, and the warehouse needed to know.

    2 · The naive version

    One class, hardwired to every interested system by name

    Works for three systems — breaks down as more show up 
    class EmailService:
    def send(self, order_id: str, message: str) -> None:
        print(f"[email] order {order_id}: {message}")

class SMSService:
    def send(self, order_id: str, message: str) -> None:
        print(f"[sms] order {order_id}: {message}")

class WarehouseService:
    def notify(self, order_id: str, status: str) -> None:
        if status == "cancelled":
            print(f"[warehouse] restocking items for order {order_id}")
        elif status == "shipped":
            print(f"[warehouse] marking order {order_id} as dispatched")


class BadOrderTracker:
    def __init__(self, order_id: str) -> None:
        self._order_id = order_id
        self._email = EmailService()
        self._sms = SMSService()
        self._warehouse = WarehouseService()

    def set_status(self, status: str) -> None:
        self._status = status
        self._email.send(self._order_id, f"order now {status}")
        self._sms.send(self._order_id, f"order now {status}")
        self._warehouse.notify(self._order_id, status)

    Run once, it works fine:

    BadOrderTracker("A-1001").set_status("shipped")
# [email] order A-1001: order now shipped
# [sms] order A-1001: order now shipped
# [warehouse] marking order A-1001 as dispatched

    Here's exactly what this costs you:

    • BadOrderTracker.__init__ constructs EmailService, SMSService, and WarehouseService itself. You can't test set_status without all three real services existing — there's no way to swap in a fake for just one of them.
    • Add the analytics system, and you have to open BadOrderTracker.set_status — code that's already written and already shipped — and add a fourth line, self._analytics.log(...). Every new interested system is an edit to this method.
    • BadOrderTracker now has four separate reasons to change: EmailService changes its method signature, SMSService does, WarehouseService does, or a new system needs wiring in. None of those are really about tracking order status — they're all about who happens to be listening.
    • You can't turn SMS off for test orders, or add a one-off observer just for a single order, without editing BadOrderTracker itself. Every order gets exactly the same fixed set of three systems notified, permanently.

    3 · Building the fix, one step at a time

    From hardwired services to a subscriber list

    Step 1 — inject the list, but keep it a mixed bag

    The smallest useful move: stop constructing the three services inside __init__, and accept them from outside as a list instead.

    class OrderTrackerListVersion:
    def __init__(self, order_id: str, watchers: list) -> None:
        self._order_id = order_id
        self._watchers = watchers

    def set_status(self, status: str) -> None:
        self._status = status
        for watcher in self._watchers:
            if isinstance(watcher, WarehouseService):
                watcher.notify(self._order_id, status)
            else:
                watcher.send(self._order_id, f"order now {status}")
    OrderTrackerListVersion("A-1001", [EmailService(), SMSService(), WarehouseService()]).set_status("shipped")
# [email] order A-1001: order now shipped
# [sms] order A-1001: order now shipped
# [warehouse] marking order A-1001 as dispatched

    This does remove the hardcoding — the call site now decides which watchers to pass in, not OrderTrackerListVersion. But look at set_status: it still has to check isinstance(watcher, WarehouseService), because EmailService.send, SMSService.send, and WarehouseService.notify don't share a method name. Add the analytics system with its own method, log_event, and you're back to editing this for loop to add another branch — the exact "editing existing code" problem from Section 2, just moved into one loop instead of three separate lines. Observer fixes this by giving every watcher the same method name, so the loop never needs to know which concrete class it's holding.

    Step 2 — give every observer the same interface

    Interface — a contract that says which methods a class must provide, without saying how they work. Example: "anything that claims to be an order observer must have an update(order_id, status) method" — that's the whole contract.
    Observer — in this pattern specifically, an object that implements a shared interface so it can be notified when something it's watching changes. Example: EmailNotifier below is an observer — it implements update, so anything that holds a list of observers can call it without knowing it's specifically an EmailNotifier. 
    from abc import ABC, abstractmethod

class OrderObserver(ABC):
    """The contract every order observer must satisfy."""

    @abstractmethod
    def update(self, order_id: str, status: str) -> None:
        """React to an order's status changing."""
        ...


class EmailNotifier(OrderObserver):
    def __init__(self, address: str) -> None:
        self._address = address

    def update(self, order_id: str, status: str) -> None:
        print(f"[email] to {self._address}: order {order_id} is now {status}")


class SMSNotifier(OrderObserver):
    def __init__(self, phone: str) -> None:
        self._phone = phone

    def update(self, order_id: str, status: str) -> None:
        print(f"[sms] to {self._phone}: order {order_id} is now {status}")


class WarehouseSystem(OrderObserver):
    def update(self, order_id: str, status: str) -> None:
        if status == "cancelled":
            print(f"[warehouse] restocking items for order {order_id}")
        elif status == "shipped":
            print(f"[warehouse] marking order {order_id} as dispatched")

    Step 3 — the subject holds observers and can add or remove them at any time

    Subject — in this pattern specifically, the object being watched. It keeps a list of observers and calls each one's update method whenever its own state changes. Example: OrderTracker below is the subject — it never imports or mentions EmailNotifier by name, it only knows it's holding a list of OrderObserver. 
    class OrderTracker:
    """Subject: holds observers and notifies them when status changes."""

    def __init__(self, order_id: str) -> None:
        self._order_id = order_id
        self._status = "placed"
        self._observers: list[OrderObserver] = []

    def attach(self, observer: OrderObserver) -> None:
        """Start notifying this observer."""
        self._observers.append(observer)

    def detach(self, observer: OrderObserver) -> None:
        """Stop notifying this observer."""
        self._observers.remove(observer)

    def set_status(self, status: str) -> None:
        self._status = status
        self._notify()

    def _notify(self) -> None:
        for observer in self._observers:
            observer.update(self._order_id, self._status)


# usage
tracker = OrderTracker("A-1001")
tracker.attach(EmailNotifier("a@b.com"))
tracker.attach(SMSNotifier("+353-000"))
tracker.attach(WarehouseSystem())

tracker.set_status("shipped")
    [email] to a@b.com: order A-1001 is now shipped
[sms] to +353-000: order A-1001 is now shipped
[warehouse] marking order A-1001 as dispatched

    OrderTracker.set_status never mentions EmailNotifier, SMSNotifier, or WarehouseSystem — it calls self._notify(), which loops over self._observers and calls observer.update(...) on each. Adding the analytics system next quarter means writing one new class, AnalyticsLogger(OrderObserver), and calling tracker.attach(AnalyticsLogger()) wherever it's needed. OrderTracker itself never changes.

    Not quite. OrderObserver defines one shared method, update, that every observer implements in its own way. A second, analytics-only method would force EmailNotifier, SMSNotifier, and WarehouseSystem to all implement something they don't need.
    Correct. That's the entire point of the shared interface: any class implementing update(order_id, status) -> None can be attached to any OrderTracker, and _notify will call it exactly like every other observer — no changes to OrderTracker required.

    4 · The shape of it

    One subject, any number of observers

    Dashed line + arrow = implements the interface. Solid gold line + diamond = holds references to, and notifies. The 0..* matters: OrderTracker can hold zero, one, or many observers, and that number can change at any time via attach/detach.

    OrderTracker never points at EmailNotifier, SMSNotifier, or WarehouseSystem specifically — only at OrderObserver, and only through a list whose length can change while the program is running. That's different from every pattern you've seen so far: Strategy and Factory Method both dealt with exactly one held reference; Observer deals with a variable-length collection of them.

    Checkpoint
    Why does OrderTracker store self._observers as list[OrderObserver] rather than, say, self._email = EmailNotifier(...), self._sms = SMSNotifier(...) as separate named fields?
    Not quite — memory isn't the reason here. A handful of object references costs essentially nothing either way; the real issue is what each design lets you do at runtime.
    Correct. self._email = EmailNotifier(...) as a named field means OrderTracker always has exactly one email observer, hardcoded into its own definition — exactly what Section 2's BadOrderTracker did. A list lets attach and detach change the membership freely, including attaching two EmailNotifier instances or zero of them, with no change to OrderTracker itself.
    Not quite — that's not a Python rule. You could technically store observers in named fields; the reason to use a list is about flexibility, not a language requirement.
    Not quite. Named fields would silently reintroduce the fixed-count, fixed-type problem from BadOrderTracker — you'd be back to editing OrderTracker's own definition every time the set of observers needed to change.

    5 · Predict the output

    What does this print? (Subscriptions change at runtime)

    t2 = OrderTracker("A-2002")
email_obs = EmailNotifier("c@d.com")
sms_obs = SMSNotifier("+353-111")

t2.attach(email_obs)
t2.attach(sms_obs)
t2.set_status("shipped")

t2.detach(sms_obs)
t2.set_status("delivered")

    Write down what the two set_status calls print, in order, before opening the answer. Pay attention to what t2.detach(sms_obs) actually does to t2._observers before the second call.

    Reveal answer 
    [email] to c@d.com: order A-2002 is now shipped
[sms] to +353-111: order A-2002 is now shipped
[email] to c@d.com: order A-2002 is now delivered

    The first set_status("shipped") notifies both observers, because both are still in t2._observers at that point. t2.detach(sms_obs) then calls self._observers.remove(sms_obs), which removes exactly that one object from the list — email_obs is untouched. So the second set_status("delivered") only reaches email_obs; sms_obs is simply no longer in the list being looped over in _notify. Nothing about OrderTracker's code changed between the two calls — only the contents of self._observers did.

    6 · Same shape, different domain

    This isn't an order-tracking-specific trick

    Observer shows up anywhere one object's state change needs to reach an open-ended group of interested parties. Two more, from unrelated domains:

    UI — button click listeners

    A UI button doesn't know or care what happens when it's clicked — an analytics system wants to record the click, a sound system wants to play a click noise, and neither should be hardcoded into the button itself.

    class ClickListener(ABC):
    @abstractmethod
    def on_click(self, button_id: str) -> None: ...

class AnalyticsClickListener(ClickListener):
    def on_click(self, button_id: str) -> None:
        print(f"[analytics] click recorded: {button_id}")

class Button:
    def __init__(self, button_id: str) -> None:
        self._button_id = button_id
        self._listeners: list[ClickListener] = []

    def add_listener(self, listener: ClickListener) -> None:
        self._listeners.append(listener)

    def click(self) -> None:
        for listener in self._listeners:
            listener.on_click(self._button_id)
    button = Button("checkout-btn")
button.add_listener(AnalyticsClickListener())
button.click()  # [analytics] click recorded: checkout-btn

    Same shape: Button.click is OrderTracker.set_status in disguise — one state change, notified out to however many listeners happen to be attached.

    Finance — a stock price ticker

    A price feed updates constantly. Several unrelated things need to react to every update: a UI widget showing the current price, and an alert engine watching for a threshold to be crossed.

    class PriceObserver(ABC):
    @abstractmethod
    def on_price_change(self, symbol: str, price: float) -> None: ...

class PriceAlertEngine(PriceObserver):
    def __init__(self, threshold: float) -> None:
        self._threshold = threshold

    def on_price_change(self, symbol: str, price: float) -> None:
        if price >= self._threshold:
            print(f"[alert] {symbol} crossed ${self._threshold:.2f}! now ${price:.2f}")

class StockTicker:
    def __init__(self, symbol: str) -> None:
        self._symbol = symbol
        self._observers: list[PriceObserver] = []

    def subscribe(self, observer: PriceObserver) -> None:
        self._observers.append(observer)

    def set_price(self, price: float) -> None:
        for observer in self._observers:
            observer.on_price_change(self._symbol, price)
    ticker = StockTicker("ACME")
ticker.subscribe(PriceAlertEngine(threshold=100.0))
ticker.set_price(95.0)    # nothing — below threshold
ticker.set_price(101.5)   # [alert] ACME crossed $100.00! now $101.50

    StockTicker.set_price doesn't know or care whether zero, one, or ten things are subscribed — same as OrderTracker.set_status.

    Three domains, one shape: a subject (OrderTracker, Button, StockTicker) holds a list of some observer interface, and one method loops over that list and calls the same method name on each — never knowing or caring how many observers there are, or what concrete classes they are.

    You've probably already used this without naming it

    Python's own logging module is built on Observer. A Logger can have several Handler objects attached, and every log call notifies all of them:

    import logging

logger = logging.getLogger("orders")
logger.addHandler(email_alert_handler)
logger.addHandler(file_handler)

logger.info("order A-1001 shipped")
# both email_alert_handler and file_handler receive this record

    addHandler is exactly attach. Internally, Logger keeps a list of handler objects and loops over it, calling handle(record) on each one — the same shape as OrderTracker._notify calling update(...) on each observer. You can attach as many handlers as you want, and logger.info(...) never needs to know how many there are.

    Checkpoint
    In logging, is Logger.addHandler(handler) playing the role of the subject's attach, or the observer's update?
    Not quite. addHandler runs once, at setup time, to register the handler — it doesn't run every time a message is logged. The method that runs per log message is the handler's own emit, which is the actual update equivalent.
    Not quite — it genuinely matches the shape: a list of registered listeners, a registration method, and a loop that calls each one when the watched state changes (a new log record). The names differ, but the mechanism is the same pattern.
    Correct. addHandler only adds the handler to Logger.handlers, a list — it does not call the handler. The handler only gets called later, once per log message, exactly like OrderTracker.attach only registers an observer without notifying it immediately.
    Not quite. addHandler only registers — it doesn't trigger anything immediately. The handler's own logic only runs on a future log call, the same separation attach and update have in this lesson's OrderTracker.

    7 · Spot the smell

    This observer unsubscribes itself — but something's wrong

    class SelfDetachingObserver(OrderObserver):
    """Watches exactly one status change, then unsubscribes."""

    def __init__(self, tracker: OrderTracker, name: str) -> None:
        self._tracker = tracker
        self._name = name

    def update(self, order_id: str, status: str) -> None:
        print(f"[{self._name}] saw order {order_id} -> {status}, unsubscribing now")
        self._tracker.detach(self)

t3 = OrderTracker("A-3003")
obs_a = SelfDetachingObserver(t3, "A")
obs_b = EmailNotifier("watcher-b@example.com")
obs_c = SelfDetachingObserver(t3, "C")
t3.attach(obs_a)
t3.attach(obs_b)
t3.attach(obs_c)

t3.set_status("shipped")

    Three observers are attached, in order: obs_a, obs_b, obs_c. obs_b is a normal EmailNotifier that never unsubscribes. Before opening the answer, predict: does obs_b's update get called during this set_status call?

    Reveal explanation 
    [A] saw order A-3003 -> shipped, unsubscribing now
[C] saw order A-3003 -> shipped, unsubscribing now

    obs_b is never called. Its update — the line that would print [email] to watcher-b@example.com: ... — silently never runs, even though it was attached and never asked to be removed.

    Here's why. OrderTracker._notify does for observer in self._observers:, which walks the list by position: index 0, then 1, then 2. When obs_a (at index 0) calls self._tracker.detach(self) from inside its own update, that runs self._observers.remove(obs_a) — while the loop is still in progress. The list shrinks from [obs_a, obs_b, obs_c] to [obs_b, obs_c], and everything shifts down one position: obs_b is now at index 0, obs_c is now at index 1. But the loop's internal position counter has already moved on to index 1 — which, after the shift, now points at obs_c, not obs_b. obs_b just got skipped, silently, with no error at all.

    This is a real, common bug with Observer: mutating the list you're currently iterating over. The fix is to iterate over a copy, so removals during the loop don't affect which positions the loop still has left to visit: for observer in list(self._observers): — that one change makes _notify loop over a separate, frozen copy of the list, so obs_b would be reached correctly even while obs_a and obs_c modify the real self._observers underneath it.

    8 · Trade-offs

    When not to reach for Observer

    Observer costs you an interface, an attach/detach/notify mechanism, and a layer of indirection between "something happened" and "code that handles it" — harder to trace than a direct function call, since finding out who reacts to a change means finding every attach call site, not just reading one method top to bottom. That's worth it once the number or identity of interested parties is genuinely variable. It's not worth it when there's exactly one thing that will ever care.

    Over-engineered 
    class SingleUseObserver(ABC):
    @abstractmethod
    def notify(self, value: int) -> None: ...

class OnlyLogger(SingleUseObserver):
    def notify(self, value: int) -> None:
        print(f"[only-logger] value is {value}")

class Counter:
    def __init__(self) -> None:
        self._observers: list[SingleUseObserver] = []
        self._value = 0

    def subscribe(self, observer: SingleUseObserver) -> None:
        self._observers.append(observer)

    def increment(self) -> None:
        self._value += 1
        for o in self._observers:
            o.notify(self._value)

    If Counter will only ever have exactly one thing watching it, forever, with no plan for a second — this is an interface, a subscribe method, and a loop, all standing in for what a single callback would say more plainly:

    class Counter:
    def __init__(self, on_change) -> None:
        self._on_change = on_change
        self._value = 0

    def increment(self) -> None:
        self._value += 1
        self._on_change(self._value)

    Reach for Observer when the set of interested parties is genuinely variable — not when it's always going to be exactly one, fixed thing.

    Observer vs. Publish/Subscribe — easy to mix up

    Both let one thing's change reach multiple listeners. The difference is whether the subject knows its observers directly.

    ObserverPublish/Subscribe
    Who holds the referencesThe subject holds direct references to its observers — OrderTracker._observers is a list of actual objectsNeither side holds the other — both talk only to a broker or message channel in between
    CouplingSubject and observer must at least agree on the observer interface, and usually live in the same processPublisher and subscriber can be completely unaware of each other, even in different processes or services
    TimingUsually synchronous — _notify calls each observer immediately, one after anotherOften asynchronous — a message sits in a queue until a subscriber is ready to read it
    One-line rule: if the notifier holds direct references to its listeners and calls them itself, it's Observer. If there's a broker or channel in between and the two sides never reference each other directly, it's Publish/Subscribe.

    9 · Cheat sheet & practice

    Cheat sheet

    Problem it solves
    One object's state change needs to reach a variable number of other objects, without that object knowing in advance who they are or how many there are.
    Core idea, in one sentence
    Give every interested party the same interface, let the subject hold a list of them with methods to add or remove members at any time, and loop over that list calling the shared method whenever the subject's own state changes.
    Trade-off
    An interface, a registration mechanism, and a layer of indirection — following what reacts to a change means finding every attach call site, not reading one method top to bottom.
    The smell that tells you to reach for it
    A method that directly calls several unrelated systems by name every time it runs, and grows a new line every time another system needs to know.
