Decorator
    Design pattern · Decorator

    Decorator

    You already know Strategy (swap behavior), Factory Method (swap which class gets built), and Adapter (make an incompatible class fit). Decorator answers a different question: how do you stack independent, optional features onto an object, in any combination, without a new subclass for every combination? Pick a notifier configuration below to see it before we name it.

    orders_service.py — the code that sends a notification
    notifier = EmailNotifier("a@b.com")
    notifier.send("Order shipped")
    Just the base notifier. No retry, no logging.

    Notice what doesn't change: the second line, notifier.send(...). Every configuration is called exactly the same way, no matter how many layers are wrapped around it. That's Decorator.

    1 · The problem

    A notification sender that needs optional features, in any combination

    You're building the part of an e-commerce backend that sends order notifications. The base behavior is simple: send an email. But different call sites need different extras layered on top. Some need automatic retry if the send fails. Some need every attempt logged for debugging. Some need both. Some need a rate limit so a batch job can't flood a customer's inbox. Every combination of these needs to actually work, and more extras — like an encryption step — are already planned for next quarter.

    Interface — a contract that says which methods a class must provide, without saying how they work. Example: "anything that claims to be a notifier must have a send(message) -> bool method" — that's the whole contract.

    Here's the first version, written when only retry and logging existed.

    2 · The naive version

    A subclass for every combination of features

    Works for two features — falls apart at three 
    class EmailNotifier:
    def __init__(self, address: str) -> None:
        self._address = address

    def send(self, message: str) -> bool:
        print(f"[email] to {self._address}: {message}")
        return True


class EmailNotifierWithRetry(EmailNotifier):
    def send(self, message: str) -> bool:
        for attempt in range(1, 4):
            print(f"[retry] attempt {attempt}")
            if super().send(message):
                return True
        return False


class EmailNotifierWithRetryAndLogging(EmailNotifierWithRetry):
    def send(self, message: str) -> bool:
        print(f"[log] sending: {message}")
        result = super().send(message)
        print(f"[log] result: {result}")
        return result

    Run once, it works:

    EmailNotifierWithRetryAndLogging("a@b.com").send("Order shipped")
# [log] sending: Order shipped
# [retry] attempt 1
# [email] to a@b.com: Order shipped
# [log] result: True

    Here's exactly what this costs you as more features and more base notifiers arrive:

    • You need logging without retry for one call site. That's a third class, EmailNotifierWithLogging, and its send body duplicates the logging lines already written inside EmailNotifierWithRetryAndLogging.
    • You need rate limiting too. Now you potentially need EmailNotifierWithRetryAndLoggingAndRateLimit, EmailNotifierWithLoggingAndRateLimit, EmailNotifierWithRetryAndRateLimit — every combination of 3 features is a separate class. With 3 optional features that's up to 7 non-trivial subclasses; with 4 features it's up to 15.
    • Add an SMSNotifier next to EmailNotifier, and the entire subclass tree has to be rebuilt a second time — SMSNotifierWithRetry, SMSNotifierWithRetryAndLogging, and so on — because none of the email subclasses' logic can be reused for SMS.
    • The retry count is fixed inside EmailNotifierWithRetry.send as the literal range(1, 4). If one call site wants 5 retries and another wants 3, that's yet another subclass or a constructor parameter threaded through every class in the chain.

    3 · Building the fix, one step at a time

    From a subclass tree to features that stack at runtime

    Step 1 — collapse the subclasses into flags on one class

    A common first instinct: stop making subclasses, and add boolean flags to one class instead.

    class EmailNotifierConfigurable:
    def __init__(self, address: str, retry: bool = False, log: bool = False) -> None:
        self._address = address
        self._retry = retry
        self._log = log

    def send(self, message: str) -> bool:
        if self._log:
            print(f"[log] sending: {message}")
        attempts = 3 if self._retry else 1
        result = False
        for i in range(attempts):
            if self._retry:
                print(f"[retry] attempt {i + 1}")
            result = self._do_send(message)
            if result:
                break
        if self._log:
            print(f"[log] result: {result}")
        return result

    def _do_send(self, message: str) -> bool:
        print(f"[email] to {self._address}: {message}")
        return True

    This does remove the subclass explosion — one class, two flags, no new class per combination. But EmailNotifierConfigurable.send is now a single method that interleaves retry logic and logging logic with if self._retry / if self._log checks throughout its body. Add a third flag, rate_limit, and you're back to editing this one already-tangled method — exactly the "editing existing, working code to add a feature" problem from Section 2, just moved from the class hierarchy into one method's control flow. Decorator fixes the deeper issue: each feature gets its own class again, but instead of subclassing, those classes wrap each other.

    Step 2 — give every notifier, wrapped or not, the same interface

    from abc import ABC, abstractmethod

class Notifier(ABC):
    """Target interface: the only notification shape our code calls."""

    @abstractmethod
    def send(self, message: str) -> bool:
        """Send message. Return True on success."""
        ...


### concrete component — the real, undecorated notifier
class EmailNotifier(Notifier):
    def __init__(self, address: str) -> None:
        self._address = address

    def send(self, message: str) -> bool:
        print(f"[email] to {self._address}: {message}")
        return True

    Step 3 — a base decorator that also implements Notifier, and holds one

    Component — in Decorator specifically, the shared interface that both the plain object and every wrapped version of it implement. Example: Notifier is the component — both EmailNotifier and every decorator around it satisfy it.
    Decorator — a class that implements the component interface, holds another component instance internally, and adds behavior before or after delegating to it. Example: NotifierDecorator below implements Notifier and holds a Notifier in self._wrapped — it can wrap an EmailNotifier, or just as easily wrap another decorator.
    Composition over inheritance — building behavior by holding a reference to another object (composition), rather than inheriting from it. Example: RetryDecorator doesn't inherit from EmailNotifier — it holds whatever Notifier it's given in self._wrapped, so it works on any notifier, not just email. 
    class NotifierDecorator(Notifier):
    """Base decorator: wraps another Notifier and forwards send by default."""

    def __init__(self, wrapped: Notifier) -> None:
        self._wrapped = wrapped

    def send(self, message: str) -> bool:
        return self._wrapped.send(message)

    NotifierDecorator is itself a Notifier — that's the detail that makes stacking possible. Anything that accepts a Notifier will accept a NotifierDecorator, which means a decorator can wrap another decorator, not just the base EmailNotifier.

    Step 4 — one small class per feature, each overriding send

    class RetryDecorator(NotifierDecorator):
    def __init__(self, wrapped: Notifier, attempts: int = 3) -> None:
        super().__init__(wrapped)
        self._attempts = attempts

    def send(self, message: str) -> bool:
        for attempt in range(1, self._attempts + 1):
            print(f"[retry] attempt {attempt}")
            if self._wrapped.send(message):
                return True
        return False


class LoggingDecorator(NotifierDecorator):
    def send(self, message: str) -> bool:
        print(f"[log] sending: {message}")
        result = self._wrapped.send(message)
        print(f"[log] result: {result}")
        return result


class RateLimitDecorator(NotifierDecorator):
    def __init__(self, wrapped: Notifier, max_per_run: int = 1) -> None:
        super().__init__(wrapped)
        self._max_per_run = max_per_run
        self._sent = 0

    def send(self, message: str) -> bool:
        if self._sent >= self._max_per_run:
            print("[rate-limit] blocked")
            return False
        self._sent += 1
        return self._wrapped.send(message)


# usage — stack any combination, in any order
notifier = LoggingDecorator(RetryDecorator(EmailNotifier("a@b.com")))
notifier.send("Order shipped")
    [log] sending: Order shipped
[retry] attempt 1
[email] to a@b.com: Order shipped
[log] result: True

    Need rate limiting on just one call site, with no retry and no logging?

    limited = RateLimitDecorator(EmailNotifier("a@b.com"), max_per_run=1)
print(limited.send("first")))   # [email] to a@b.com: first  ->  True
print(limited.send("second")))  # [rate-limit] blocked        ->  False

    No new class was needed for that combination — RateLimitDecorator wraps EmailNotifier directly, skipping RetryDecorator and LoggingDecorator entirely. Every feature is independent, and none of them know the others exist.

    Checkpoint

    4 · The shape of it

    A decorator implements the interface it also holds

    Dashed line + arrow = implements the interface. Solid gold line + diamond = holds a reference to. The gold line looping back from NotifierDecorator to Notifier — the same interface it implements — is what makes stacking possible.

    This loop is the one detail that separates Decorator from every other pattern you've seen so far. NotifierDecorator both is a Notifier (dashed arrow up) and holds a Notifier (gold line back). Because what it holds can be EmailNotifier, or another NotifierDecorator, wrapping LoggingDecorator around RetryDecorator around EmailNotifier is just three objects, each holding the next.

    Checkpoint
    Why must NotifierDecorator implement Notifier itself, rather than just holding one?
    Not quite — this isn't just style. Drop the inheritance and RetryDecorator would no longer satisfy the wrapped: Notifier parameter that LoggingDecorator.__init__ expects, so stacking two decorators together would stop type-checking and stop working.
    Correct. LoggingDecorator(RetryDecorator(EmailNotifier(...))) only works because RetryDecorator — a decorator — can itself be passed anywhere a Notifier is expected. That's precisely because NotifierDecorator inherits from Notifier. Remove that, and decorators could only ever wrap EmailNotifier directly, never each other.
    Not quite — that's not a real Python rule. Plenty of classes hold references to objects of unrelated types. The reason here is specific to Decorator: the wrapper needs to be usable everywhere the thing it wraps is usable.
    Not quite. This lesson's code doesn't rely on isinstance checks anywhere — NotifierDecorator's send method is called polymorphically, the same way every other pattern in this series has used inheritance. The stacking behavior itself is the real reason.

    5 · Predict the output

    What does this print? (Wrap order matters)

    FlakyEmailNotifier fails on its first call and succeeds after that:

    class FlakyEmailNotifier(Notifier):
    def __init__(self, address: str) -> None:
        self._address = address
        self._calls = 0

    def send(self, message: str) -> bool:
        self._calls += 1
        if self._calls == 1:
            print(f"[email] to {self._address}: FAILED to send '{message}'")
            return False
        print(f"[email] to {self._address}: {message}")
        return True

    Compare these two, built from the exact same three classes, just nested in the opposite order:

a.send("Order shipped")

# ---

b = RetryDecorator(LoggingDecorator(FlakyEmailNotifier("a@b.com")))
b.send("Order shipped")

    In a, LoggingDecorator is outermost, so [log] sending and [log] result print exactly once each — logging wraps the whole retry loop as one unit. RetryDecorator's loop runs underneath, invisible to logging except for its final outcome.

    In b, RetryDecorator is outermost, so its loop is what calls LoggingDecorator.send — and that means LoggingDecorator runs fresh on every retry attempt, printing a full sending/result pair each time. Same three classes, same call, twice the log lines — because wrap order decides which decorator's loop the others live inside.

    6 · Same shape, different domain

    This isn't a notification-specific trick

    Decorator shows up anywhere independent extras need to stack onto a base object, in any combination, without multiplying subclasses. Two more, from unrelated domains:

    Payments — fees stacking on a charge

    A checkout total starts as a base charge. International cards add a fee. Currency conversion adds another. Either, both, or neither can apply to a given transaction.

    class Charge(ABC):
    @abstractmethod
    def amount_cents(self) -> int: ...

class BaseCharge(Charge):
    def __init__(self, amount_cents: int) -> None:
        self._amount = amount_cents
    def amount_cents(self) -> int:
        return self._amount

class ChargeDecorator(Charge):
    def __init__(self, wrapped: Charge) -> None:
        self._wrapped = wrapped
    def amount_cents(self) -> int:
        return self._wrapped.amount_cents()

class CurrencyConversionFee(ChargeDecorator):
    def amount_cents(self) -> int:
        return self._wrapped.amount_cents() + 150

class InternationalFee(ChargeDecorator):
    def amount_cents(self) -> int:
        return self._wrapped.amount_cents() + 300
    total = InternationalFee(CurrencyConversionFee(BaseCharge(5000)))
print(total.amount_cents())  # 5450

    Same shape: ChargeDecorator is a Charge that holds a Charge — fees stack by nesting, and any subset of fees can apply without a subclass for each combination.

    UI — text formatting

    A text renderer might need to apply bold, italic, or both, to the same underlying text, in either order.

    class TextRenderer(ABC):
    @abstractmethod
    def render(self, text: str) -> str: ...

class PlainText(TextRenderer):
    def render(self, text: str) -> str:
        return text

class RendererDecorator(TextRenderer):
    def __init__(self, wrapped: TextRenderer) -> None:
        self._wrapped = wrapped
    def render(self, text: str) -> str:
        return self._wrapped.render(text)

class Bold(RendererDecorator):
    def render(self, text: str) -> str:
        return f"**{self._wrapped.render(text)}**"

class Italic(RendererDecorator):
    def render(self, text: str) -> str:
        return f"_{self._wrapped.render(text)}_"
    styled = Bold(Italic(PlainText()))
print(styled.render("Shipped"))  # **_Shipped_**

    Bold and Italic never know about each other, exactly like RetryDecorator and LoggingDecorator never know about each other — each just wraps whatever TextRenderer it's given.

    Three domains, one shape: a decorator base class (NotifierDecorator, ChargeDecorator, RendererDecorator) implements the same interface it wraps, so any number of concrete decorators can be nested around a base object, in any order, in any subset.

    You've probably already used this without naming it

    Python's own @decorator syntax is named after this pattern for a reason. A function decorator wraps a callable and returns something that can be called the exact same way:

    import functools

def with_retry(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        for attempt in range(1, 4):
            print(f"[fn-retry] attempt {attempt}")
            result = fn(*args, **kwargs)
            if result:
                return result
        return result
    return wrapper

@with_retry
def flaky_call():
    ...

    with_retry plays exactly RetryDecorator's role: it takes something callable, returns something equally callable, and adds behavior around the call. The class-based version from this lesson and Python's @ syntax are the same idea — one applies to objects with several methods, the other to single functions.

    Checkpoint
    @with_retry above wraps flaky_call. What role is wrapper (the inner function returned by with_retry) playing, in Decorator terms?
    Not quite. Nothing here defines a formal interface — Python functions are all callable the same way by default, so there's no explicit component contract to point to. That's part of why this version is lighter-weight than the class-based one.
    Not quite — that's flaky_call itself, captured as fn inside wrapper. wrapper is the thing wrapped around it, not the original behavior.
    Correct. wrapper closes over fn — the equivalent of self._wrapped — and is itself callable the same way fn is, exactly like RetryDecorator is itself a Notifier that holds a Notifier.
    Not quite. The mechanism looks different — closures instead of classes and inheritance — but the shape is identical: something that holds the original behavior, exposes the same calling convention, and adds logic around the call.

    7 · Spot the smell

    This is a decorator — but something's wrong

    class BrokenLoggingDecorator(NotifierDecorator):
    def __init__(self, wrapped: Notifier) -> None:
        pass  # TODO: set self._wrapped somehow

    def send(self, message: str) -> bool:
        print(f"[log] sending: {message}")
        result = self._wrapped.send(message)
        print(f"[log] result: {result}")
        return result

    BrokenLoggingDecorator inherits from NotifierDecorator, exactly like LoggingDecorator did. Something's still wrong. What happens when you construct it and call send?

    Reveal explanation 
    broken = BrokenLoggingDecorator(EmailNotifier("a@b.com"))
broken.send("Order shipped")
# [log] sending: Order shipped
# AttributeError: 'BrokenLoggingDecorator' object has no attribute '_wrapped'

    The bug: __init__ overrides NotifierDecorator.__init__ but never calls super().__init__(wrapped) — and never sets self._wrapped any other way. The wrapped argument is accepted and then silently discarded. [log] sending prints fine, because that line doesn't touch self._wrapped — but the very next line, self._wrapped.send(message), crashes, because that attribute was never set on this instance at all.

    This is a version of a bug that shows up constantly with decorators: overriding __init__ in a subclass without calling the parent's __init__, either directly or through super(). Every concrete decorator that needs its own constructor — like RetryDecorator, which also stores attempts — must call super().__init__(wrapped) first, so the one piece of state every decorator relies on, self._wrapped, actually gets set.

    8 · Trade-offs

    When not to reach for Decorator

    Decorator costs you an extra base class and a wrapper class per feature — more indirection to step through when reading a stack trace, since a call to send might pass through three or four objects before doing real work. That's worth it once features genuinely combine independently. It's not worth it when there's only ever going to be one fixed feature.

    Over-engineered 
    class Notifier(ABC):
    @abstractmethod
    def send(self, message: str) -> bool: ...

class EmailNotifier(Notifier):
    ...

class NotifierDecorator(Notifier):
    def __init__(self, wrapped: Notifier) -> None:
        self._wrapped = wrapped
    def send(self, message: str) -> bool:
        return self._wrapped.send(message)

class HashingDecorator(NotifierDecorator):
    def send(self, message: str) -> bool:
        message = hash_message(message)  # always applied, everywhere, no exceptions
        return self._wrapped.send(message)

    If every single message, at every call site, forever, must be hashed before sending — with no call site that ever skips it — this is four classes and one layer of indirection for something a single line inside EmailNotifier.send would say more plainly: message = hash_message(message) before the print. Reach for Decorator when a feature is genuinely optional and needs to combine with other optional features — not when it's really a mandatory step of the base behavior that always runs.

    Decorator vs. Proxy — easy to mix up

    Both wrap an object and implement the same interface as what they wrap. The difference is why you're wrapping it, and whether the caller is meant to notice.

    DecoratorProxy
    GoalAdd new behavior the caller explicitly chose (retry, logging, rate limiting)Control or manage access to the real object, transparently (lazy loading, permission checks, caching)
    Does the caller choose itYes — LoggingDecorator(RetryDecorator(...)) is deliberately assembled by the code that constructs itOften no — a factory or framework hands you a proxy and you use it exactly like the real thing, unaware it's not
    StackingDesigned to stack — several decorators, in any order, is the normal caseUsually one layer — you don't typically stack five proxies around one object
    One-line rule: if the caller is deliberately opting into extra behavior by choosing what to wrap with, it's Decorator. If the wrapper exists to manage access to the real object without the caller needing to know or care, it's Proxy.

    9 · Cheat sheet & practice

    Cheat sheet

    Problem it solves
    Several independent, optional features need to combine on top of a base object, in any subset and any order, without a subclass for every combination.
    Core idea, in one sentence
    Write a base decorator that implements the same interface as the object it wraps and holds one instance of that interface, then give each feature its own small decorator subclass that adds behavior before or after delegating to what it wraps.
    Trade-off
    More classes and more indirection — a single call can pass through several wrapper layers before doing real work, which makes stack traces longer to read.
    The smell that tells you to reach for it
    A subclass tree (or a single class full of boolean flags) trying to represent every combination of optional features on the same base behavior.
